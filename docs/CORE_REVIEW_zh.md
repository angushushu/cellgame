# 核心接口检查与下一步

目前最值得保留的结构是“观察 → 本地决策 → 行动提议 → 服务端裁决”。它允许更换 GUI、模型和物种控制方式，同时让世界代价与实际影响留在服务器。标准应围绕这条链固定，避免把网页状态当成游戏协议。

本轮将能独立验证的部分写成 `CORE_STANDARD_zh.md` 的 1.0.0-rc.1，并落实到公开入口、注册表、Schema、跨语言样例和测试。候选标准的版本与 Python 包版本分别管理。

| 检查项 | 原有问题 | 本轮处理 |
| --- | --- | --- |
| 对外入口 | 第三方需要从 GUI / sim_process 等内部模块挑函数 | 增加 `cellgame.api`，玩家运行时移到 species，结算移到 server.kernel |
| 版本协商 | 未来版本可能被当成兼容版本接受 | 明确支持列表求交，拒绝未知版本；保留旧版回退 |
| 跨语言数组 | 原生字节序和隐式 dtype 假设不明确 | 固定小端、C 顺序、紧密表；校验长度和数值类型 |
| 行动输入 | 小数、bool 或大整数可能在转换中被截断 | 从规则适配、本地服务到网络入口先校验再转换 |
| 行动时序 | 错误 / 未来时刻消息可能占用后续提交位置 | 仅在有效当前时刻提议通过后记录已提交 |
| 感知含义 | 兼容表不能区分未知与空地；材料未进入简易 SDK | 增加 observed、材料和群系读取，未知返回 None |
| 有机体身份 | Entity 对象每轮重建，身份来源不清 | 暴露服务端 entity_id 和 world_run，结算后先刷新身份 |
| 本地 ML | HTTP / stdio 分别校验，格式可能漂移 | 共用请求结构和响应动作校验器 |
| 符合标准的依据 | 只有同一套 Python 端互测不够 | 加入二进制黄金样例和独立 JS 解码测试 |

下一阶段建议按下面顺序推进，分别形成标准扩展：

1. **通用环境层及材料注册。** 现在有 food、temp、biomes、materials，但任意世界的材料名称、可感知字段、单位和规则说明还不能随清单完整发布。可以新增独立 layers / materials 扩展版本，声明 ID、显示元数据和感知策略；客户端渲染根据元数据适配。具体伤害和收益仍由世界代码裁决。这比继续把更多材料硬编码进 GUI 更有价值。
2. **持久 Unity 与通讯约束。** 当前 Unity 是本地组合视图。如果要让“群体意识”成为游戏机制，需要明确成员关系、身份延续、连接权限、消息带宽 / 延迟，以及只有边界输入能进入群体时的限制。不能只靠类继承实现这些规则；在这一设计完成前，标准明确不承诺权威 Unity。
3. **统一世界命令与生命周期事件。** 当前 after_actions 只报告成功进食，on_event 与生态钩子的命令集合不同。下一版宜使用有类型的事件与命令，并明确每个阶段读到什么、改变什么、失败是否回滚；迁移旧钩子时提供适配器。现有“先验证整批命令”只保证输入验证阶段，不是整轮事务回滚。
4. **跨实现重放与同步。** 目前 tick、身份和结果足以连接第三方客户端，但完整的确定性回放、世界版本摘要、断线恢复和 delta 缺失重同步还没标准化。做第二个独立实现时，应增加同一输入序列的结果对照。
5. **拆分发行包。** 先维持统一公开入口，再把 shared、species 运行时、server.kernel 和权威世界依赖抽成 core 发行包，GUI 作为可选依赖。拆包前需要独立安装测试，确保内核不会间接导入网页或网络服务。当前已验证公开入口不导入客户端，尚未发布独立 core 包。

3D 应作为几何及观察格式的新版本加入，继续保留二维适配器；不要现在给已有二维表随意加列。先让第三方能用已固定的二维协议写出另一套客户端，会更直接地检验标准是否完整。
